## 12.16 Back-of-the-Envelope Toolkit for ML System Design

### Conceptual Deep Dive
Estimation in an interview is a derivation with stated assumptions, not a recall test. Say each assumption aloud, mark it as a rule of thumb, and invite correction. Module 12 section 7 (legacy) lists the formulas; this section shows how to chain them.

**Traffic and storage.** Average QPS = DAU x actions per user per day / 86,400; peak QPS = average x peak factor. Choose the factor from the traffic shape (rule of thumb: 2-3x for smooth consumer traffic, 10x or more for event-driven spikes such as sales, payday or market open). An underestimated peak factor is the most common error. Storage = events per day x bytes per event x retention days x replication x (1 + index overhead); replication and indexes often double the raw figure. Online store memory = entities x bytes per entity x replication; raw feature bytes understate real memory because of keys and allocator overhead, so budget about 2x raw (rule of thumb). Training cost = GPU-hours x hourly rate, with the rate a parameter, never a quoted price.

**Compute.** Little's law gives concurrency L = throughput x latency, so busy cores = peak QPS x service time. Replicas = ceil(busy cores / target utilisation / workers per replica), plus N+1 or zone headroom. Keep utilisation near 0.5-0.7 because queueing delay grows sharply as it approaches 1 (module 6 section 7 (legacy) covers the tail). For accelerators, divide peak items per second by the measured items per second per device. Averages fail under skew: when a hot partition takes 10x its share, size for the hottest shard.

**Latency budget.** Serial hops add, parallel hops cost the maximum, and p99s do not sum exactly, so hold 20-30% slack (rule of thumb).

| Hop | Budget (ms) | Parallel? |
|---|---|---|
| Gateway + auth | 5 | no |
| Feature lookups (3 stores) | 15 | yes, cost = slowest |
| Model inference | 20 | no |
| Rules + response | 10 | no |

**Cost.** Cost per 1k predictions = instance cost per hour / predictions per hour x 1000. Batch usually wins on unit cost (high utilisation, amortised overhead) and loses on freshness; compute the ratio from the same formula with each mode's utilisation and throughput.

**Worked set.** Fraud scoring: 5M DAU x 8 transactions gives about 460 average QPS and about 4.6k at 10x peak. Feed feature store: 50M users x 40 features gives 16 GB raw and roughly 77 GB with overhead and two replicas. Nightly batch: window hours = rows / (rows per second per worker x workers x 3600); check it fits before the morning deadline with 30% slack.

Do not design for 100x traffic that will not occur. Size for 3-5x with a named path beyond it.

### Production Anti-Patterns
- Giving a single number with no assumptions: nobody can challenge or update it, and the interviewer cannot see your reasoning.
- Ignoring peak versus average: the service is sized for the mean and falls over on the first spike or hot key.
- Designing for 100x traffic that will not occur: cost and complexity are paid every day for a load that never arrives.

### Minimal Working Code
An estimator module and a table for the fraud example.

```python
import math

def qps(dau, actions, peak_factor):
    avg = dau * actions / 86400
    return avg, avg * peak_factor

def replicas(peak_qps, service_s, util=0.6, workers=4):
    return math.ceil(peak_qps * service_s / util / workers)

def storage_gb(events_day, bytes_ev, days, repl=3, index=0.3):
    return events_day * bytes_ev * days * repl * (1 + index) / 1e9

def online_gb(entities, bytes_ent, repl=2, overhead=2.0):
    return entities * bytes_ent * overhead * repl / 1e9

def cost_per_1k(rate_per_hour, preds_per_hour):
    return rate_per_hour / preds_per_hour * 1000

if __name__ == "__main__":
    avg, peak = qps(5_000_000, 8, 10)
    n = replicas(peak, 0.015)
    per_hour = 4 / 0.015 * 0.6 * 3600
    rows = [("avg QPS", avg), ("peak QPS", peak), ("replicas", n),
            ("storage GB", storage_gb(avg * 86400, 1000, 365)),
            ("online GB", online_gb(50_000_000, 40 * 8 + 64)),
            ("cost/1k (rate=1.0, hypothetical)", cost_per_1k(1.0, per_hour))]
    for name, v in rows:
        print(f"{name:34s}{v:14,.4f}")
    assert n == math.ceil(peak * 0.015 / 0.6 / 4)
```

A sensitivity helper that answers "what would change my mind".

```python
def sweep(peaks, utils, services, dau=5_000_000, actions=8, rate=1.0):
    print("peak  util  svc_ms  replicas  monthly_cost")
    base = None
    for pf in peaks:
        for u in utils:
            for s in services:
                _, pk = qps(dau, actions, pf)
                n = replicas(pk, s / 1000, u)
                cost = n * rate * 730
                base = base or n
                print(f"{pf:4d}  {u:4.1f}  {s:6d}  {n:8d}  {cost:12,.0f}  x{n / base:.2f}")

sweep([5, 10, 20], [0.5, 0.7], [15, 30])
assert replicas(qps(5_000_000, 8, 20)[1], 0.015) > replicas(qps(5_000_000, 8, 10)[1], 0.015)
```

The first row is the baseline; the last column shows which assumption moves capacity most. Here the service time and peak factor scale replicas linearly, while utilisation scales by its inverse.

### Interview Angle
**Q:** Estimate infrastructure for a 5k-QPS fraud scoring service with a 100 ms p99 budget.
**A:** Assume 15 ms mean service time, so busy cores = 5,000 x 0.015 = 75. At 0.6 utilisation and 4 workers per pod that is ceil(75 / 0.6 / 4) = 32 pods, plus N+1 per zone. I would budget 5 ms gateway, 15 ms parallel lookups, 20 ms inference, leaving slack. Trade-off: lower utilisation buys tail latency but costs pods. Check: a load test at 1.5x peak must hold p99 under 100 ms, and the pod count should change when I vary the peak factor.

**Q:** Size the online feature store for 50M users with 40 features each.
**A:** Raw is 50M x 40 x 8 bytes = 16 GB. Add key and per-entity overhead (rule of thumb 2x), giving about 38 GB, then two replicas gives about 77 GB. Trade-off: fewer, quantised or hashed features and shorter TTLs cut memory, but cost accuracy or freshness. Check: load a 1% sample into the real store, read memory per entity, and extrapolate rather than trust my constant.

## 12.17 Behavioural and Staff-Level Communication for MLOps Loops

### Conceptual Deep Dive
Behavioural rounds score judgement and ownership, and in MLOps loops they decide level more often than candidates expect. Prepare a **story bank** of six stories: a drift incident, a rollout, a cost cut, a reproducibility fix, a cross-team conflict and a failed project. Structure each with STAR (situation, task, action, result), but add two items most candidates omit: a number (what moved, by how much, over what window) and a prevention outcome (what control now exists so it cannot recur). Link each story to the technical sections that back it, so follow-up questions land on prepared ground.

**Seniority signals** are visible in how you speak. Scoping: you narrow an ambiguous request before solving it. Trade-off narration: you name the rejected alternative and the cost of your choice. Risk anticipation: you describe what you monitored and the rollback path. Mentoring and influence without authority: you changed a standard through evidence, a pilot or a written proposal. Writing: you can produce a clear design doc or RFC.

**Ambiguity and pushback.** Restate the question in one sentence, propose explicit assumptions, and check in ("is that the direction you want?"). If you do not know, say so, give the nearest thing you do know and describe how you would find out. Never bluff a tool detail.

**Non-ML stakeholders.** Use a metric tree that connects the model metric to a business outcome, frame risk as cost of wrong decisions, and ask for a decision with a deadline rather than attention.

**Staff-level topics** include org-level leverage (one platform fix that removes a class of incidents), platform bets and their exit costs, deprecation plans, build-versus-buy politics, and RFC authoring: problem, options, recommendation, risks, rollout, success metric. Reference 16.1 and 16.5.

**Red flags** interviewers note: reciting tools instead of decisions, blaming other teams, taking credit for team results without specifics, and no lessons learned. Edge cases: a story with no measurable outcome (estimate honestly and say it is an estimate), answering a different question than asked (confirm the question first), and over-long answers (aim for two minutes, then offer to go deeper).

- Reciting tools instead of decisions: the listener learns your stack, not your judgement or what you would do differently.
- Taking credit for team results without specifics: follow-ups expose the gap between "we" and what you personally decided.
- No lessons learned: a story that ends at the fix signals that the same incident can recur.

### Minimal Working Code
A story-bank validator that prints practice gaps.

```python
import re

REQUIRED = ["situation", "action", "result", "lesson", "section"]

def validate(story):
    gaps = [k for k in REQUIRED if not str(story.get(k, "")).strip()]
    if story.get("result") and not re.search(r"\d", story["result"]):
        gaps.append("result has no number")
    if story.get("section") and not re.fullmatch(r"\d+\.\d+", story["section"]):
        gaps.append("section must look like 8.16")
    return gaps

BANK = {
    "drift": {"situation": "Null rate rose after an upstream deploy",
              "action": "Added a contract test and rollback runbook",
              "result": "Detection time fell from 2 days to 20 minutes",
              "lesson": "Own the interface, not just the model", "section": "8.16"},
    "cost": {"situation": "Inference bill grew", "action": "Batched requests",
             "result": "Cheaper and faster", "lesson": "", "section": "16.4"},
}

if __name__ == "__main__":
    for name, s in BANK.items():
        print(name, "->", validate(s) or "ok")
    assert validate(BANK["drift"]) == []
    assert "lesson" in validate(BANK["cost"])
```

A timed-answer helper that splits a two-minute answer into segments.

```python
SPLIT = {"context": 0.2, "action": 0.4, "result": 0.25, "learning": 0.15}

def budgets(total_s=120, wpm=140):
    return {k: int(total_s * f / 60 * wpm) for k, f in SPLIT.items()}

def check(segments, total_s=120, wpm=140):
    warn = []
    for k, limit in budgets(total_s, wpm).items():
        n = len(segments.get(k, "").split())
        if n > limit:
            warn.append(f"{k}: {n} words > {limit} (~{n / wpm * 60:.0f}s)")
    return warn

answer = {"context": "word " * 30, "action": "word " * 120, "result": "word " * 20,
          "learning": "word " * 10}
print(budgets())
print(check(answer))
assert check(answer) == ["action: 120 words > 112 (~51s)"]
```

Tune `wpm` to your own speaking pace by timing a recorded answer.

### Interview Angle
**Q:** Tell me about a time you pushed back on a stakeholder to protect model quality.
**A:** Frame it as a trade-off, not a refusal. For example, a launch date forced a skipped holdout; I proposed a smaller staged rollout with a gate on a named slice, showed the expected cost of a bad release, and agreed a rollback trigger. Trade-off: a one-week delay against uncapped risk. Result to state: the number the gate caught or the incident avoided, and the control that remained afterwards. Mention what you would concede next time.

**Q:** Describe a platform decision you would defend as a staff engineer, and the alternative you rejected.
**A:** For example, a golden path with managed defaults over letting each team pick tools. Rejected alternative: full freedom, which maximises local speed but multiplies on-call burden and audit work. Trade-off: less flexibility for lower operational cost. Measurable check: time to first production model, share of models on the path, and incident count per model, reviewed quarterly with a stated condition for revisiting the decision.
